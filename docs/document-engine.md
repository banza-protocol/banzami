# Document Engine & Official Receipts

The **Document Engine** is the single, shared system that generates official
Banzami PDF documents server-side. There is one engine, one template, and one
visual identity for every surface (consumer app, merchant app, BANZADMIN).

Apps never build PDFs locally — the official document is always generated by the
backend from canonical data.

---

## Where it lives

| Path | Role |
|------|------|
| `services/common/documents/` | Shared Go module (`github.com/banzami/banzami/services/common/documents`) — the engine: `ReceiptData`, `RenderHTML`, `GeneratePDF`, `Filename`, the receipt HTML template. No dependency on email/Resend, business logic, or the ledger. |
| `go.work` | Go workspace so `public-api`, `api-gateway`, and `admin-api` all build against the shared module. |

In each consuming service `go.mod` carries
`replace github.com/banzami/banzami/services/common/documents => ../common/documents`,
and the Docker build context contains `common/` + the service as siblings (see
`deploy.sh`) so the replace resolves identically locally and in Docker.

The engine is **read-only**: callers pass typed data already read from the
canonical sources and it renders the official design. It never persists anything.

---

## Server-side PDF generation

The engine renders the receipt HTML template, then prints it to A4 PDF with a
**headless Chromium**:

- The browser binary is resolved from `BANZAMI_CHROME_BIN` (falls back to common
  install paths). Chromium is installed in the runtime image of every service
  that generates PDFs (`public-api`, `api-gateway`, `admin-api`).
- Generation has a timeout; if no browser is available it returns an error
  (never panics) and the HTTP layer responds `503` — independent of any other
  flow.
- Temporary files are written to a per-request temp dir and removed after use.

`ReceiptData` supports three perspectives — `CONSUMER`, `MERCHANT`, `ADMIN` —
which only change copy (e.g. *Comprovativo de transferência* vs *Comprovativo de
pagamento recebido*); the layout is identical.

## Canonical data sources (read-only)

| Document | Source | Service |
|----------|--------|---------|
| Consumer transfer receipt | `transfers` (by id) — owner must be sender or recipient | `public-api` |
| Merchant payment receipt | `wallet_payments` (by id or settling `transfer_id`) — scoped to the merchant + token environment | `api-gateway` |
| Admin receipt | `wallet_payments` first, else `transfers` | `admin-api` |

Party names/handles are resolved from `consumers` / `merchants`. No new tables,
no ledger or core changes — the engine consumes existing canonical records.
`wallet_payments` is the first-class wallet-native merchant payment object.

## Endpoints

All require authentication; ownership is enforced (a caller never sees another
party's transaction — `404`, never revealing existence).

| Method · Path | Service | Auth | Returns |
|---|---|---|---|
| `GET /v1/consumer/transactions/{id}/receipt.pdf` | public-api | Consumer JWT | `application/pdf` |
| `GET /v1/merchant/wallet-payments` | api-gateway | Merchant JWT | JSON list (keyset cursor) |
| `GET /v1/merchant/transactions/{id}/receipt.pdf` | api-gateway | Merchant JWT | `application/pdf` |
| `GET /admin/v1/wallet-payments` | admin-api | Operator JWT + `merchant.view` (audited) | JSON list |
| `GET /admin/v1/transactions/{id}/receipt.pdf` | admin-api | Operator JWT + `merchant.view` (audited) | `application/pdf` |

PDF responses set
`Content-Disposition: inline; filename="banzami-comprovativo-<reference>.pdf"`
and `Cache-Control: private, no-store`.

Listing items carry the `id` used by the matching `receipt.pdf` endpoint plus
`receipt_available`. List filters: `status`, `date_from`, `date_to`, `limit`,
`cursor` (admin also `merchant_id`, `environment`).

Responses by data state: with no matching transaction → `404`; an empty list →
`200` with `items: []`. A missing/blocked transaction is never a `500`.

## Mobile: local PDF generation removed

Local on-device PDF generation has been removed from the apps. The Flutter SDK
no longer ships a PDF builder or the `pdf` dependency.

- **Consumer app** — the *Comprovativo* action calls
  `ConsumerPublicClient.fetchReceiptPdf(transactionId)` and shares the returned
  PDF. Offline / `403` / `404` are handled with clear messages.
- **Merchant app** — a *Recebidos* tab lists real `wallet_payments` via
  `BanzamiClient.listMerchantWalletPayments(...)`; the *Comprovativo* action
  calls `BanzamiClient.fetchMerchantReceiptPdf(id)` and shares the PDF.

## BANZADMIN

A **Pagamentos recebidos** page lists `wallet_payments` (distinct from the
*Pagamentos* / payouts page) with status/environment filters and a
*Comprovativo* action that opens the official PDF. Access is gated by the
`merchant.view` capability and recorded in the admin audit log.

---

## Security

Receipts and the engine never include API keys, PINs, tokens, signed URLs or
bank data. Action links carry a token in the URL only inside the email/app flow,
never in receipts. Logs never print secrets; PDF generation failures surface as a
generic `503`.

## Operational note

The merchant/admin surfaces require the `wallet_payments` table
(`db/migrations/0046_wallet_payments.sql`). The consumer receipt only depends on
`transfers`. With no data yet, list endpoints return an empty list and receipt
endpoints return `404`.
